# Phase 3 — Modularity and duplication review (instructions §12 phase 3 item 3)

Scope: `src/config`, `src/data/metrics` (production + `__tests__` helpers). Report only; nothing under metrics-data-layer was edited.
Already known and not re-reported: L1 (row-cap semantics), L2 (compileWhere `toDateOnly` copy), L5 (4.2–4.4 items-by-id population), L6 (two loader envelope helpers). Where a finding touches one of these, it says so and covers only the new part.
Method: read every loader, derive, compute helper, shared loader, fake and OSDK adapter file, loadCard, catalogue, selection, breakdowns; ran an exported-symbol usage scan (production vs test references); grepped for numeric and string literals outside `src/config` (fixtures excluded as test data); reproduced the D24 progress heuristic in node (scratch `ps.mjs`).

Config-leak scan result: outside fixtures and `source/osdk`, production code has no numeric literals other than 0/1 (only the `section: 1 | 2` literal type). The string literals are almost all typed codes (caveats, stage ids, window keys, dims) derived from the config tuples. The real leaks are hand-copied stage lists and bucket lists (MOD-09, MOD-10), key-label strings (MOD-17), the `slice(0, 10)` date length (MOD-13), and the abort message (MOD-14).

## Summary
- Majors: 4.
  - **MOD-01**: the D24 progress heuristic in `loadCard.createProgressSum` gives wrong, too-low totals whenever fetches run one after another or interleave (reproduced). Replace it with per-call delta sinks, which is also simpler.
  - **MOD-02**: the MAX_GROUPS `truncated` rule is computed in both the loaders and the derives, and the copies already differ (4.1 has no derive check; the userFunnel escalated and item-view candidates lists differ). Keep it in derive only; the L6 envelope then shrinks to the row-cap and window-cap caveats.
  - **MOD-03**: the fake re-implements the 4.1 verdict gate, verdict field and date window instead of reusing `compute/otifOutcome` (D8 spirit), and the copies differ on date-only handling.
  - **MOD-04**: five loaders keep private copies of breakdown-registry knowledge (alert-attribute dims, event group fields, open-alert filter dims, item dims). Export the guards from `breakdowns.ts`.
- No blockers. There are 16 minors, all concrete and mechanical: shared helper extraction, stage and bucket lists back to config, dead-code removal, abort-helper consolidation, test-kit consolidation, and tighter layering checks.
- Config-leak scan: clean for numeric literals. String leaks are limited to hand-copied stage and bucket lists, key labels, the date-length 10, and the abort message (MOD-09, 10, 13, 14, 17).
